# Wire contract v1 — phone agent ⇄ office service

Authoritative interface between the phone capture agent and the office service. The Python
reference implementations (`server/commscap/{phone,redact,gate,wire}.py`) define the behaviour of
the shared logic; `shared/vectors/*.json` (generated by `tools/gen_vectors.py`) are the
cross-language test vectors. **If the phone and the server disagree about a vector, the phone is
wrong.**

All times are epoch milliseconds (`*_ms`) unless a header says seconds. All numbers in tests are
fictional (206-555-01xx).

## 1. Transport and auth

HTTPS, JSON bodies (UTF-8), base URL configured on the phone (e.g. `https://comms.example.com`).

Every request except the media download carries:

| Header | Value |
|---|---|
| `X-Device-Id` | device id configured on the phone (e.g. `michael-phone-1`) |
| `X-Timestamp` | current epoch **seconds** |
| `X-Signature` | lowercase hex `HMAC-SHA256(secret, "{ts}.{device_id}.{sha256_hex(body_bytes)}")` |

`body_bytes` is the exact request body (empty for GET). The server rejects a timestamp more than
300 s from its clock (replay window) and any bad signature with `401`. See `wire_vectors.json`.

A `401` means "this phone is not authorised / clock is wrong": **do not delete queued messages**,
stop retrying hot, show the problem on the status screen, keep heartbeating at the normal cadence.

## 2. Message identity

`uid = sha256_hex("{device_id}|{direction}|{address}|{ts_ms}|{sha256_hex(body_utf8)}|{media_count}")`

`address` is the E.164 number when the address is a phone number, otherwise the trimmed raw
address. The `uid` is the idempotency key everywhere (queue, upload, reconcile, de-dup). See
`wire_vectors.json`. The body used for the uid is the **redacted** body that is uploaded.

## 3. Capture-side behaviour (what the phone must do)

For every message seen (incoming or outgoing, SMS/MMS, plus RCS notifications — see §8):

1. `PhoneNumber.classify(address)` → `kind`, `e164` (vectors: `phone_vectors.json`).
2. `Redact.redact(body)` → redacted body + tags (vectors: `redact_vectors.json`). Redaction happens
   before anything is queued, logged or shown.
3. `Gate.decide(policy, address, redactedBody, hasMedia, contactSaved, contactLabels)`
   (vectors: `gate_vectors.json`):
   * `send`  → enqueue for upload (durable, survives reboot/force-stop).
   * `drop`  → **nothing is stored or uploaded**; only increment the 24 h counter. No body, no
     address, no hash is persisted for dropped messages.
   * `defer` → (keyword mode, or a blank text) keep on the phone (durable) up to `policy.defer_hours`;
     upload later only if the same address produces a `send` (the "thread lookback": when address A
     yields `send`, enqueue A's deferred messages that are still within `defer_hours`, oldest first,
     *before* the new one). Expire silently (delete) after `defer_hours`.
   * `hold`  → media with no text from an unknown number: keep on the phone up to
     `policy.hold_media_days`, never upload automatically, count it in the heartbeat.
4. Direction `out` uses the same gate on the counterpart's address (Michael's outgoing texts to
   family are never captured). For `send` decisions on outgoing messages nothing else changes.

`contactSaved` / `contactLabels` come from the phone's Contacts (READ_CONTACTS) for the counterpart
number. Contact lookup results are used for the gate only; `contact_name` is uploaded only for
messages that pass the gate.

## 4. `POST /v1/ingest`

Request body:

```json
{
  "schema": 1,
  "device_id": "michael-phone-1",
  "sent_at_ms": 1789999999000,
  "policy_version": "2026-11-21.1",
  "messages": [
    {
      "uid": "<64 hex>",
      "direction": "in",
      "transport": "sms",
      "address": "(206) 555-0101",
      "contact_name": "Heidi Walsh",
      "contact_saved": true,
      "contact_labels": ["AAAD Clients"],
      "ts_ms": 1789999999123,
      "body": "ok thanks",
      "redactions": [],
      "media": [{"mime": "image/jpeg", "size": 123456, "sha256": "<64 hex>"}],
      "thread_key": "android-thread-id-or-null",
      "gate": {"decision": "send", "reason": "allow_client", "rule_version": "gate-1"}
    }
  ]
}
```

* `transport`: `sms` | `mms` | `notification` (RCS/chat message seen only as a notification; inbound only).
* At most 20 messages per request. `media` lists attachments by hash; the bytes are NOT in this request.
* `contact_name` may be null. `address` is sent raw; the server normalises it.

Response `200`:

```json
{
  "ok": true,
  "accepted":   ["<uid>"],
  "duplicates": ["<uid>"],
  "rejected":   [{"uid": "<uid>", "reason": "server_gate_drop"}],
  "media_wanted": [{"uid": "<uid>", "sha256": "<64 hex>"}],
  "policy_version": "2026-11-21.2",
  "thread_verdicts": [{"address": "+12065550177", "verdict": "business"}],
  "server_time_ms": 1789999999500
}
```

Phone behaviour on the response:

* `accepted` and `duplicates`: delete from the upload queue (the server has them durably).
* `rejected`: delete from the queue and **do not retry** (`server_gate_drop`, `bad_schema`, `stale`).
  A `server_gate_drop` means the server's own gate disagreed; count it and move on.
* `media_wanted`: upload those attachments (§5). Media is uploaded **only** when listed here.
* `policy_version` differs from the stored one → `GET /v1/policy` soon (within the minute).
* `thread_verdicts`: `business` → add the address to a local `provisional_business` overlay (so the
  rest of that thread passes the gate immediately); `private` → add to a local `exclude_numbers`
  overlay AND delete any queued / deferred / held messages from that address. The overlay is
  merged with the downloaded policy and survives policy refreshes.
* `5xx`, `429`, network error, timeout → keep everything, exponential backoff 15 s → 30 s → … cap
  15 min, with jitter. Never delete on a failure.
* Other `4xx` (not 401/429): do not delete; mark the batch failed, show it on the status screen,
  retry on the normal schedule (do not hot-loop).

## 5. `PUT /v1/media/{uid}/{sha256}`

Raw bytes, `Content-Type` = the media mime type, signed like every other request (body = the bytes).
Response `200 {"ok": true}`. Idempotent. Only for items in `media_wanted`. Stream from the
content resolver; do not load huge files fully into memory. Retry like ingest.

## 6. `GET /v1/policy`

Signed, empty body. Response is the on-device gate policy (same shape as `gate_vectors.json` →
`policy`): `version`, `numbers` (e164 → `client|crew|vendor|agency`), `exclude_numbers`,
`provisional_business`, `client_labels`, `drop_sender_kinds`, `business_terms`,
`job_number_pattern`, `address_pattern`, `defer_hours`, `hold_media_days`, `unknown_policy`
(`"ai_all"` default: every text from an unsaved, non-allowlisted number is sent for AI screening;
`"keyword"`: only texts with a business signal are sent, the rest `defer`). Cache it; until the first
successful download use a built-in default policy (empty numbers, default terms/patterns from the
Python `DEFAULT_BUSINESS_TERMS` / `JOB_NUMBER_PATTERN` / `ADDRESS_PATTERN`).

## 7. `POST /v1/heartbeat`

Every 15 minutes (and after every successful ingest if the last heartbeat is older than 5 min):

```json
{
  "schema": 1, "device_id": "michael-phone-1", "ts_ms": 1789999999000,
  "app_version": "0.1.0", "policy_version": "2026-11-21.1",
  "queue_depth": 0, "deferred_depth": 3, "held_depth": 0, "oldest_queued_ms": null,
  "last_capture_ts_ms": 1789999000000, "last_upload_ok_ms": 1789999500000,
  "permissions": {"sms": true, "contacts": true, "notification_listener": true,
                  "battery_unrestricted": true, "post_notifications": true},
  "counters_24h": {"seen": 120, "sent": 14, "dropped": 90, "deferred": 15, "held": 1},
  "capture_paused_until_ms": null,
  "nudge_acks": ["n_123"]
}
```

Response `200`:

```json
{ "ok": true, "server_time_ms": 1789999999500, "policy_version": "2026-11-21.1",
  "nudges": [ { "id": "n_123", "level": 1, "title": "Reply due: Heidi Walsh",
                "text": "Bid question 2h ago (26-4708)", "address": "+12065550101",
                "deadline_ms": 1790003599000 } ] }
```

The heartbeat response may also carry `"media_wanted": [{"uid": "<uid>", "sha256": "<64 hex>"}]`
(same meaning as in the ingest response, §4/§5) and `"thread_verdicts": [...]` (same as §4): screening
is asynchronous, so a verdict can arrive after the ingest response. Apply both exactly as for ingest.

Each nudge not yet acked is shown **once** as a high-importance notification; tapping it opens the
SMS thread for `address` in the default messaging app (`sms:` intent). Ack the id in the next
heartbeat. A `nudge_acks` list is how the server knows Michael's phone actually displayed it.

## 8. `POST /v1/reconcile` (nightly, ~02:30 local, and on demand from the status screen)

```json
{ "schema": 1, "device_id": "michael-phone-1",
  "window_start_ms": 1789913599000, "window_end_ms": 1789999999000,
  "expected_uids": ["<uid>", "..."] }
```

`expected_uids` = every uid the phone's gate decided `send` for in the window, **including ones
already acknowledged** (rescan the system SMS/MMS store for the window to compute it; do not rely
only on the queue). Response: `{"ok": true, "missing": ["<uid>"], "known": 17}`. For each missing
uid the phone rebuilds the message from the system store and enqueues it again. Window = last 48 h.

## 9. `POST /v1/mark` (Michael's one-tap privacy control and corrections)

```json
{ "schema": 1, "device_id": "michael-phone-1", "address": "+12065550177",
  "verdict": "private", "uid": "<optional uid>" }
```

`verdict` ∈ `private` (purge everything stored from that address and exclude it forever) |
`business` (treat the address as a business thread from now on). Phone applies the same local
overlay change as for `thread_verdicts` immediately, then posts (queue the post if offline).
Response `{"ok": true}`.

## 10. Android capture sources (RCS caveat)

* Incoming SMS: `SMS_RECEIVED` broadcast. Outgoing SMS and all MMS: observe `content://sms` and
  `content://mms` (cursor per table, last seen `_id` persisted) plus a WorkManager catch-up scan
  every 15 minutes and at boot — the observer alone is not trusted.
* **RCS / "chat" messages do not appear in the SMS/MMS provider.** The agent therefore also runs a
  `NotificationListenerService` for the default messaging apps (`com.google.android.apps.messaging`,
  `com.samsung.android.messaging`) and captures *incoming* messages from their notifications
  (`transport = "notification"`), de-duplicated against SMS by (address, body, ±60 s). Outgoing RCS
  cannot be captured. Recommended operational setting: turn **RCS chats off** in the messaging app
  so everything flows through SMS/MMS and both directions are captured. The status screen must show
  whether the notification-listener permission is granted.
* Sideloaded app on Android 13+: SMS and notification-access permissions are "restricted settings";
  the user must open App info → ⋮ → "Allow restricted settings" before granting. The setup screen
  must explain this in plain words.

## 11. What the status screen must show Michael (transparency is a design requirement)

* Capturing: on / paused (with remaining time) / a permission is missing (which one, with a button).
* Last text seen, last successful upload, queue depth.
* Today's counters (seen / sent to office / kept private on phone).
* A list of the last 20 messages sent to the office: contact, time, first 40 characters,
  and a **"This was private"** button on each (→ `/v1/mark` private, plus local purge).
* Pause capture (1 h / until tomorrow). A pause is reported in the heartbeat; the server alerts
  the office if it lasts > 4 h.

## 12. Non-goals / hard rules

* No upload of anything the gate `drop`ped, `deferred` (until promoted) or `hold`s.
* No contact-list upload. No call-log. No location.
* No plaintext secret in logs. Logs never contain message bodies.
* No third-party analytics/crash SDKs.
